# AGENTS.md

Operating manual for this repository (Grinning Cat core — CAT). Read this before changing agent lifecycle code.

## Agent deletion protocol

The teardown of one agent is a single resumable protocol owned by `cat/looking_glass/agent_deletion.py`. Treat the delete marker as the only source of truth for "is this agent fully gone".

- **Marker key.** Each agent has exactly one teardown marker at `agents:<id>:ingestion:delete`, written with **no TTL** (`cat/looking_glass/agent_deletion.py:105-107`, `:125-136`). Invariant: **marker present <=> teardown incomplete**. Never clear it before memory and files are gone (`agent_deletion.py:376-379`). Marker reads are presence-only, so both the core schema `{"delete_marker": True, "started_at": ...}` and the plugin schema `{"delete_marker": True}` count (`agent_deletion.py:138-146`).
- **Entry point.** `CheshireCat.destroy()` writes the marker first, then delegates to `complete_agent_teardown(agent_id, ccat=self)` and shuts the instance down (`cat/looking_glass/cheshire_cat.py:100-124`). Routes call it through an `AuthorizedInfo` cat instance (`cat/routes/utilities.py:167`, `:190`).
- **Order of the teardown.** Inside `agent-delete:<id>`, in this order: return early when the marker is absent; capture the file list from the live cat; quiesce ingestion; run the per-source deletion cascade; run the blanket `destroy_memory()` catch-all; remove the file folder; wipe the `agents:<id>:*` namespace preserving the marker; fire `after_cheshire_cat_destroy`; clear the marker **last** (`agent_deletion.py:339-393`, `:245-300`). Source capture happens **before** the cascade because the cascade needs the list while it is still readable. The per-source cascade runs, for each source, `before_file_manager_file_delete` while the point metadata still exists → `delete_tenant_points` for that source → `after_file_manager_file_deleted`; only afterwards does the blanket `destroy_memory()` purge everything not tied to a captured source (`agent_deletion.py:245-300`). The cascade runs **before** the wipe, so a crash there leaves the marker plus the intact namespace and recovery retries the cascade. The destroy hook fires **after** the wipe: a plugin handler may delete and re-store the marker (EffING's `clear_agent`), which is harmless once the namespace holds only the marker; firing it before the wipe could lose the marker while the master key/settings/conversations still existed. A crash after the wipe leaves only the marker.
- **Marker-only recovery short-circuit.** When `ccat` is `None` and the agent namespace holds only the delete marker, `complete_agent_teardown` clears the marker without booting a light cat. This is only reachable **after the cascade and the wipe already ran**, so nothing is left to purge; a crash at the very end must not leave a permanently stuck marker (`agent_deletion.py:344-349`, `:306-309`).
- **Creation rollback.** On any failure during `create_cheshire_cat` — `BaseException`, so `CancelledError` also triggers it — `rollback_cheshire_cat_creation` tears the agent down through the marker + teardown protocol: a live cat is destroyed directly, otherwise the marker is written first and `complete_agent_teardown` is called, leaving a resumable marker on failure (`bill_the_lizard.py:218-245`).
- **Quiesce.** `wait_for_ingestion_quiesce` scans `agents:<escaped_id>:ingestion:*`, skips the marker itself, and treats a row as busy unless its `status` is terminal (`completed`/`error`); terminal-first means an unknown status keeps the agent busy (`agent_deletion.py:36-39`, `:167-207`). Quiesce is bounded assurance, not a hard gate: on timeout it logs a warning and the teardown proceeds because the marker makes workers self-abort.
- **Environment variables and lock budgets.** `CAT_INGESTION_DELETE_QUIESCE_SECONDS` (default `180`), `CAT_INGESTION_DELETE_POLL_SECONDS` (default `5`) (`agent_deletion.py:41-43`, `:330-332`), `CAT_DELETE_COMPLETION_ON_BOOT` (default `true`) (`cat/env.py:35`, `cat/looking_glass/bill_the_lizard.py:32-35`). The teardown lock budget is `_teardown_lock_budget(quiesce) = 2*quiesce + 300` seconds (`agent_deletion.py:93-104`), covering quiesce, cascade, purge, wipe, light-cat boot/shutdown and hooks with headroom. The create lock budget is `_create_lock_budget(quiesce) = teardown_budget + 60`, so it strictly outlives the nested teardown plus the create work itself (`bill_the_lizard.py:42-53`, `:187-190`).
- **Boot completion.** `_schedule_delete_completion()` runs `complete_pending_deletes()` as a fire-and-forget task when `CAT_DELETE_COMPLETION_ON_BOOT` is truthy, after `after_lizard_bootstrap` (`bill_the_lizard.py:119-123`, `:125-135`). Recovery scans `agents:*:ingestion:delete`, derives the id from the key, and isolates failures per agent (`agent_deletion.py:391-416`).
- **Policy A — create meets a pending delete.** `create_cheshire_cat` takes `agent-create:<id>` for the whole critical section; if a delete marker is present it first runs `complete_agent_teardown(agent_id)` and only then checks whether the agent exists (`bill_the_lizard.py:139-176`). The `agent-create:<id>` lock also serialises duplicate creates of the same id, so two concurrent creates cannot both pass the existence check and build two agents (`bill_the_lizard.py:145-167`). An existing agent returns the existing instance (`bill_the_lizard.py:177-178`).
- **Lock ordering rule.** The core create path takes `agent-create:<id>` and, through the teardown it triggers, `agent-delete:<id>`; the core delete path never takes `agent-create:<id>`, so no cycle exists (`bill_the_lizard.py:158-163`). The ghost-cleanup CLI is the deliberate exception: in `--apply` it takes `agent-create:<id>` to serialise against a concurrent create, then performs only a direct `crud.destroy` (never the `agent-delete:<id>` teardown), so it cannot form a cycle (`migrations/cleanup_ghost_agents.py:177-201`). Keep this ordering in any new caller.
- **Re-entrancy constraint.** Re-entrancy is ENFORCED by a task-local `ContextVar` guard (`_ACTIVE_OPERATIONS`, `agent_deletion.py:55-87`). A plugin hook fired inside create or destroy (`after_cheshire_cat_creation`, `after_cheshire_cat_destroy`) that calls the same operation for the **same** agent id raises `RuntimeError` immediately, before touching any lock, instead of self-blocking until the timeout. A `create` → teardown transition for the same id stays legitimate (different operations); `create`→`create` and `delete`→`delete` do not. Dispatch work for the same id to a different task or a different id instead.
- **Connection to the system namespace.** `complete_agent_teardown` wipes only `agents:<id>:*`; `system:*` keys are not touched by it, so the system agent is not deletable through this path (`agent_deletion.py:214-220`).
- **Ghost definition.** A ghost is an agent with peripheral keys (`settings:*`, `conversations:*`, `users:*`, `plugins:*`, `ingestion:*`) but no master key `agents:<id>:agent` (`migrations/cleanup_ghost_agents.py:2-8`, `:161-174`). Ghosts carry no marker, so boot completion does not touch them.
- **Cleanup CLI contract.** `migrations/cleanup_ghost_agents.py` is a destructive, manually-run maintenance script, not part of startup or the alembic chain (`:10-11`). Dry-run is the default and exits `2` without writing; `--apply` is required for any mutation; `--json` prints the machine-readable report; exit codes are `0` ok, `1` partial failure, `2` aborted / nothing done (`:13-32`, `:204-237`). Each agent is processed in isolation, and agents holding their master key or a delete marker are skipped (`:19-20`, `:161-174`). It uses `cat.db.crud` only, never a raw client (`:26-28`). In `--apply` every candidate is re-classified and destroyed while holding `agent-create:<id>` (60s timeout, `:71`, `:177-201`), closing the window where a create lands between classification and destroy and leaves a live agent hollowed out; if the lock cannot be acquired the candidate is reported under `failed` and nothing is deleted. Dry-run takes no lock and writes nothing. A namespace whose id contains `:` (a scanned key whose second segment is not a known family: `agent`, `settings`, `conversations`, `users`, `plugins`, `ingestion`) is reported as `ambiguous_id` and is never classified or deleted, in dry-run and in `--apply`, and a candidate namespace that is a strict prefix of an ambiguous one is guarded the same way because `agents:<id>:*` also matches `agents:<id>:<more>:*` (`:80-95`, `:122-158`, `:204-237`). An id whose continuation segment is itself a known family token (e.g. `team:settings`) is indistinguishable from `<id>:<family>` and is NOT covered by the guard; it is tracked by the blocked charset decision (todo 10).
- **Plugin contract (cross-repo).** A plugin treats ingestion for an agent as canceled when the delete marker is present **or** the master key `agents:<id>:agent` is gone; both reads go through `cat.db.crud` (`/root/git/plugins/cat-efficient-ingestion/registry.py:119-125`). Consequences for plugins: stop writing status once canceled, and never assume the marker appears before the namespace wipe — the master key can vanish first.
- **Glob escaping.** Agent ids are user-controlled (`POST /agents/create`), so every Redis pattern built from an id goes through `_escape_glob`, which escapes `\ * ? [ ]` with backslash first (`agent_deletion.py:55-67`, `migrations/cleanup_ghost_agents.py:52-62`). Never interpolate a raw id into a pattern.
- **Idempotency.** `complete_agent_teardown` returns immediately when the marker is gone, so a late duplicate call is safe; a crash mid-teardown leaves a marker that boot completion resumes (`agent_deletion.py:312-388`, `:391-416`).

## Ingestion host APIs for plugin authors

These are the host-side contracts ingestion plugins build on. They are additive and stable.

- **Chunker stamps (`cat/services/factory/chunker.py`).** Every chunk produced by `Chunker.split_documents` carries `chunk_index` (0-based ordinal within the call; one call == one logical source) and `start_index` (monotonic character offset of the chunk in its source, re-derived from the source text so it stays correct across overlap). A pre-existing `chunk_index` is preserved (`setdefault`), so a caller that numbers chunks itself keeps its own values.
- **Document-provided point id (`cat/rabbit_hole.py:551-558`).** `store_documents` uses `id=doc.id or uuid.uuid4().hex`: a `Document` that already carries an `id` (e.g. a catalogue card's deterministic `uuid5`) is stored under that id and a re-ingest upserts instead of duplicating; documents without an id keep the random `uuid4` fallback. The efficient engine's store/embed phases follow the same rule (the parsing store honours `Document.id`, the embed re-store carries the stored point id).
- **`cat.db.cruds.settings.get_ingestion_status_keys(agent_id)` (`cat/db/cruds/settings.py:338`).** Agent-scoped, **read-only** enumeration of `agents:<agent_id>:ingestion:*` for ingestion plugins. It escapes the untrusted agent id with `escape_glob`, never writes or deletes, and does not filter the delete marker (callers decide what to do with it).
- **`CustomHookVetoException` (`cat/exceptions.py:32`).** A hook raises it to veto the operation it gates (e.g. the ingestion completion gate). The hook dispatcher (`cat/looking_glass/mad_hatter/mad_hatter.py:359`) **re-raises** it instead of logging and swallowing it, so the veto short-circuits the remaining hooks and reaches the caller as an error.
- **`escape_glob` (`cat/db/crud.py:170`).** Escapes `\ * ? [ ]` (backslash first) so an untrusted value (agent id, source name) interpolated into a Redis glob cannot widen the match. Use it for every pattern built from user-controlled input.
