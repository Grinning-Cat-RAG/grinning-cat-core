# AGENTS.md

Operating manual for this repository (MyCAT core). Read this before changing agent lifecycle code.

## Agent deletion protocol

The teardown of one agent is a single resumable protocol owned by `cat/looking_glass/agent_deletion.py`. Treat the delete marker as the only source of truth for "is this agent fully gone".

- **Marker key.** Each agent has exactly one teardown marker at `agents:<id>:ingestion:delete`, written with **no TTL** (`cat/looking_glass/agent_deletion.py:50-52`, `:70-80`). Invariant: **marker present <=> teardown incomplete**. Never clear it before memory and files are gone (`agent_deletion.py:284-287`). Marker reads are presence-only, so both the core schema `{"delete_marker": True, "started_at": ...}` and the plugin schema `{"delete_marker": True}` count (`agent_deletion.py:83-89`).
- **Entry point.** `CheshireCat.destroy()` writes the marker first, then delegates to `complete_agent_teardown(agent_id, ccat=self)` and shuts the instance down (`cat/looking_glass/cheshire_cat.py:100-124`). Routes call it through an `AuthorizedInfo` cat instance (`cat/routes/utilities.py:167`, `:190`).
- **Order of the teardown.** Inside `agent-delete:<id>`, in this order: return early when the marker is absent; capture the file list from the live cat; quiesce ingestion; wipe the `agents:<id>:*` namespace preserving the marker; purge vector memory; run the per-source deletion cascade; remove the file folder; fire `after_cheshire_cat_destroy`; clear the marker **last** (`agent_deletion.py:245-294`, `:192-237`). Source capture happens **before** the wipe because the wipe deletes the stored file settings (`agent_deletion.py:273-282`).
- **Quiesce.** `wait_for_ingestion_quiesce` scans `agents:<escaped_id>:ingestion:*`, skips the marker itself, and treats a row as busy unless its `status` is terminal (`completed`/`error`); terminal-first means an unknown status keeps the agent busy (`agent_deletion.py:36-39`, `:112-156`). Quiesce is bounded assurance, not a hard gate: on timeout it logs a warning and the teardown proceeds because the marker makes workers self-abort.
- **Environment variables.** `CAT_INGESTION_DELETE_QUIESCE_SECONDS` (default `180`), `CAT_INGESTION_DELETE_POLL_SECONDS` (default `5`) (`agent_deletion.py:41-43`, `:255-256`), `CAT_DELETE_COMPLETION_ON_BOOT` (default `true`) (`cat/env.py:35`, `cat/looking_glass/bill_the_lizard.py:32-35`). The delete lock budget is `quiesce + 120` seconds (`agent_deletion.py:257`).
- **Boot completion.** `_schedule_delete_completion()` runs `complete_pending_deletes()` as a fire-and-forget task when `CAT_DELETE_COMPLETION_ON_BOOT` is truthy, after `after_lizard_bootstrap` (`bill_the_lizard.py:119-123`, `:125-135`). Recovery scans `agents:*:ingestion:delete`, derives the id from the key, and isolates failures per agent (`agent_deletion.py:297-322`).
- **Policy A — create meets a pending delete.** `create_cheshire_cat` takes `agent-create:<id>` for the whole critical section; if a delete marker is present it first runs `complete_agent_teardown(agent_id)` and only then checks whether the agent exists (`bill_the_lizard.py:139-176`). The `agent-create:<id>` lock also serialises duplicate creates of the same id, so two concurrent creates cannot both pass the existence check and build two agents (`bill_the_lizard.py:145-167`). An existing agent returns the existing instance (`bill_the_lizard.py:177-178`).
- **Lock ordering rule.** The create path takes `agent-create:<id>` and, through the teardown it triggers, `agent-delete:<id>`. The delete path never takes `agent-create:<id>`, so no cycle exists (`bill_the_lizard.py:158-163`). Keep this ordering in any new caller.
- **Re-entrancy constraint.** A plugin hook fired inside create or destroy (`after_cheshire_cat_creation`, `after_cheshire_cat_destroy`) must not call create/destroy for the **same** agent id: the nested acquisition blocks on a lock already held by the same critical section until the timeout (`bill_the_lizard.py:164-167`). Dispatch work for the same id to a different task or a different id instead.
- **Ghost definition.** A ghost is an agent with peripheral keys (`settings:*`, `conversations:*`, `users:*`, `plugins:*`, `ingestion:*`) but no master key `agents:<id>:agent` (`migrations/cleanup_ghost_agents.py:2-8`, `:99-112`). Ghosts carry no marker, so boot completion does not touch them.
- **Cleanup CLI contract.** `migrations/cleanup_ghost_agents.py` is a destructive, manually-run maintenance script, not part of startup or the alembic chain (`:10-11`). Dry-run is the default and exits `2` without writing; `--apply` is required for any mutation; `--json` prints the machine-readable report; exit codes are `0` ok, `1` partial failure, `2` aborted / nothing done (`:13-28`, `:150-155`, `:189-217`). Each agent is processed in isolation, and agents holding their master key or a delete marker are skipped (`:19-20`, `:128-143`). It uses `cat.db.crud` only, never a raw client (`:21-22`).
- **Plugin contract (cross-repo).** A plugin treats ingestion for an agent as canceled when the delete marker is present **or** the master key `agents:<id>:agent` is gone; both reads go through `cat.db.crud` (`/root/git/plugins/cat-efficient-ingestion/registry.py:119-125`). Consequences for plugins: stop writing status once canceled, and never assume the marker appears before the namespace wipe — the master key can vanish first.
- **Glob escaping.** Agent ids are user-controlled (`POST /agents/create`), so every Redis pattern built from an id goes through `_escape_glob`, which escapes `\ * ? [ ]` with backslash first (`agent_deletion.py:55-67`, `migrations/cleanup_ghost_agents.py:52-62`). Never interpolate a raw id into a pattern.
- **Idempotency.** `complete_agent_teardown` returns immediately when the marker is gone, so a late duplicate call is safe; a crash mid-teardown leaves a marker that boot completion resumes (`agent_deletion.py:246-265`, `:284-294`).
